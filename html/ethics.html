Ethics & privacy reflection

What does it mean to handle a student's data responsibly?

StudyFlow stores what a student is working on and when it is due. This page reflects on the ethical and privacy decisions behind that simple fact.

Privacy: collecting the minimum, keeping it local

A task list is surprisingly personal. It reveals which courses a student is enrolled in, how far behind they are, and what they are worried about. Because of this, the most important design decision in StudyFlow was a negative one: the application collects no personal data and sends it nowhere. Tasks are saved in the browser's localStorage on the user's own device, there is no server, no account system backed by a database, and no analytics or tracking of any kind.

This is an application of the principle of data minimisation — only collect what the product strictly needs. StudyFlow needs task titles, course details and due dates to function; it does not need a real name, email address, phone number or student ID, so it never asks for them. Had this been a server-backed app, each of those fields would have become a liability: something to store securely, to protect from breaches, and to justify.

The demonstration login — an honest limitation

The task manager is gated by a basic username and password login, as required by the specification. It is important to be honest about what this is: a client-side demonstration, not real security. The credentials are checked in JavaScript, which means anyone can read them by viewing the source. A production system would verify credentials on a server, hash passwords with a slow algorithm such as bcrypt, lock accounts after repeated failures, and use HTTPS to protect credentials in transit. Documenting that gap — rather than pretending the demo login "secures" anything — is itself an ethical obligation to the marker and to anyone reading this code.

Ethical design: honesty, fairness and inclusion

Beyond privacy, three ethical commitments shaped the interface. First, honesty: the countdown and overdue styling tell the user the truth about their deadlines instead of gamifying false urgency — there are no manipulative "streaks" designed to induce guilt. Second, fairness: the validation rules reject invalid input with clear, specific messages rather than silently guessing what the user meant, because silent "corrections" of someone's data are a small act of disrespect. Third, inclusion: the pages use semantic landmarks, labelled form fields, visible focus states, keyboard-operable dialogs and colour contrast that meets WCAG AA, so the app remains usable by students who navigate with a keyboard or screen reader.

Accessibility as an ethical issue

During testing I navigated the whole app with the keyboard alone, and it changed how I think about "extra" features. A modal that traps focus and can be closed with Escape is not polish — for some students it is the difference between using the app and being locked out of it. Similarly, colour never carries meaning on its own: overdue tasks are red and labelled "Overdue", so colour-blind users receive the same information. Accessibility failures exclude people; treating it as a core requirement, not an afterthought, is the ethical baseline for any interface.

If StudyFlow grew up

Scaling this app would create real obligations: syncing tasks to a server would require encryption in transit and at rest, a published privacy policy, compliance with laws such as the Australian Privacy Principles and, for broader use, the GDPR; account deletion would need to actually delete data; and third-party libraries would need auditing before being trusted with user data. The local-first design of this assignment defers all of those risks rather than solving them — and recognising when a design decision avoids a problem entirely is, I have learned, as important as solving it.

Key takeaways

  • Collect the minimum: every stored field is a permanent responsibility.
  • Local-first design protects users by default — no server, no breach surface.
  • Be honest about limitations: a demo login is not security, and saying so matters.
  • Accessibility is an ethical requirement, not an optional enhancement.
